# Scene RSI Experiment 1：Natural Reconstruction Trajectory Analysis

现在开始一个独立的三维场景重建研究工程，并实际完成第一批自然重建轨迹实验。

## 1. 研究背景

已有工程：

- https://github.com/i025/scene
- https://github.com/i025/hintrsi

之前的 Scene RSI 工程部分继承了 SceneEvolve 的 Harness、工具或重建策略。

之前的代码题 RSI 已经实现历史轨迹分析、知识提取、持久知识注入及独立测试，但没有充分证明轨迹学习优于教师先验知识，也没有证明状态对齐和多轮更新能够稳定提高学生能力。

历史代码实验还发现：

- 不同知识库可能具有较高的语义重合度。
- 不同学生运行可能采用相似的技术实现。
- 相同最终成绩可能对应完全不同的执行进度。
- 知识进入学生上下文不等于学生真正使用知识。

现在将研究重点转回 Image-to-3D Scene Reconstruction。

本次不开展完整 RSI，而是建立属于我们自己的独立实验环境，并回答自然重建轨迹是否存在策略冗余、互补知识及重复性能力缺陷的问题。

## 2. 研究问题

RQ1：同一个基础模型，在相同任务、相同初始 Harness 和相同预算下，独立重建同一张图片时，求解轨迹有多大差异？

RQ2：不同重建轨迹是否反复出现相同的视觉、几何、材质、物体结构与空间关系缺陷？

RQ3：不同轨迹是否包含值得后续学习的互补建模方法？

RQ4：哪些重建问题可能仅靠总结已有轨迹难以解决，需要教师主动引导新的探索方向？

以上均为待研究问题，不预设轨迹一定高度重合，也不预设所有重复性错误都属于基础模型能力缺陷。

本次不加入教师 Hint，不进行 Skill 学习，不进行 Harness Evolution，不进行 Meta-Agent Evolution，不训练模型。

新建独立工程，暂定名称 `scene-rsi`。

不要在原 scene 实验目录中覆盖已有实验。

不要继承 SceneEvolve 的：

- Prompt。
- Skill。
- 建模函数库。
- 工具调用策略。
- 任务分解流程。
- 演化后的 Harness。
- 历史 Memory。
- 教师反馈。

允许复用已有服务器上的：

- Blender 安装与 Python 环境。
- Codex CLI 安装和已验证的模型接入方式。
- 通用日志记录方式。
- 通用进程管理和渲染环境配置。
- 不包含重建策略的基础设施代码。

明确记录复用了什么，没有复用什么。

代码风格尽量与我们已有工程一致，简单直接。

不要添加哈希验证、校验和系统、复杂防御性工程、多层抽象或预防假想问题的代码。

不要重复下载已经存在的模型、Blender、Python 包和数据。

这是共享服务器，不能影响其他用户的 CPU、内存、GPU、磁盘或正在运行的任务。

优先使用当前可用资源。初期优先考虑 CPU 渲染；如果存在空闲 GPU 且允许使用，可以在统一实验配置下使用。不得占用正在被其他任务使用的 GPU。

所有需要模型参与的操作使用 Codex CLI。

学生模型统一为 `gpt-6.1-terra`，reasoning effort 为 `low`。先核验实际可用的模型标识，不得静默切换其他模型。

建议总墙钟预算六小时，包括环境准备、数据选择、预检、正式运行、监控和报告。

优先使用：

https://huggingface.co/datasets/IDEAL-Benchmark/IDEAL-Scenes

https://ideal3d.github.io/

正式选择：

- 一个卧室场景。
- 一个厨房场景。

优先选择物体数量适中、存在多个家具或复杂部件、具有一定材质差异，并且能够在现有环境下实际打开和重新渲染的场景。

每个场景至少需要：

- 原始参考 RGB 图片。

- 相机元数据（如果提供）。

- 物体、几何和材质是否存在。

保存原始参考图，不要覆盖。

如果某个样本缺少 `.blend` 或必要资源，优先寻找同类别的其他完整样本。

如果整个数据来源无法使用，可以选择有完整 Blender 文件的官方开放场景作为替代，但要记录数据来源、许可和替换原因。

官方 Blender 场景：

https://www.blender.org/download/demo-files/

不得在看到学生重建表现以后重新挑选更有利的场景。

## 11. 独立场景质量分析

所有学生运行完成后，再开始评价。

评价端可以访问 GT。

分开评价以下维度，不要将它们强行合成为单一综合分数：

### 11.1 参考视角视觉一致性

观察：

- 可见物体。
- 物体外观。
- 场景布局。
- 材质与纹理。
- 颜色。
- 相机视角。
- 光照与阴影。
- 整体参考图像恢复程度。

如本地已有合适的图像相似度模型，可以复用作为辅助指标，但不要为了本次实验重复下载大型模型。

模型评分只能作为自动评价，不能冒充人类审美评分。

### 11.2 三维结构合理性

分析：

- 物体遗漏或多余。
- 物体尺度及比例。
- 物体相对位置。
- 朝向。
- 部件连接。
- 支撑关系。
- 明显穿插或悬空。
- 可编辑性。
- 单一视角下被掩盖的结构问题。

不同 Blender 对象的命名、拆分数量和网格结构可以不同。

不能直接要求学生对象名、Mesh 数量或顶点数量与 GT 相同。

必要时先建立语义物体对应关系，明确一对多或多对一的匹配。

单图重建具有尺度和遮挡歧义。绝对坐标误差只有在合理统一坐标系与尺度之后才有意义。

若无法可靠对齐，不报告具有误导性的精确误差。

区分参考图像可见的结构、GT 中存在但单图不可辨识的结构，以及普遍三维合理性问题。

不要把包围盒相交直接当作真实网格接触或穿插的充分证据。

### 11.3 技术完成度

记录：

- Blender 代码是否执行成功。
- 最终 .blend 是否存在及可打开。
- 最终渲染是否完成。
- 外部材质资源是否完整。
- 最终代码是否能够重新生成交付场景。
- 是否只是用参考图片平面代替真实三维重建。
- 是否出现提前结束或不完整交付。

保留失败和中断案例。

## 12. 自然轨迹多样性分析

先建立清晰的分析标签体系，再统一应用于九次运行。

建议分析维度：

A. 任务分解策略
- 是否显式识别主要物体。
- 是否进行部件级分解。
- 是否进行场景关系分析。
- 布局优先、物体优先或其他策略。

B. 几何建模策略
- 基础几何体拼接。
- 参数化建模。
- 曲线建模。
- 整体网格。
- Modifier。
- 实例化。
- 其他实际出现的技术。

C. 空间布局策略
- 独立绝对坐标。
- 局部坐标。
- 相对位置计算。
- 物体关系约束。
- 其他方法。

D. 材质与纹理策略
- 纯色材质。
- 程序化纹理。
- 图像映射。
- 节点组合。
- UV 或其他坐标映射。
- 其他实际方法。

E. 相机与渲染策略
- 固定相机。
- 迭代调整。
- 投影关系估计。
- 光照调整。
- 其他技术。

F. 自检及恢复策略
- 是否观察自己生成的渲染。
- 是否进行局部检查。
- 是否检查几何或场景状态。
- 是否发现错误。
- 是否实际修复。
- 修复后是否验证。

上述标签只用于事后分析，不提供给学生。

允许发现新的策略类别。

每个标签应尽量引用实际代码、工具事件、场景状态或渲染证据。

对于无法确认的情况标记 unknown，不要填成未采用。

## 13. 轨迹相似度与重复性缺陷

对于每个场景的三次独立运行，计算三个两两组合。

三个场景共九个同任务配对。

分别分析：

### Strategy Overlap

根据有证据支持的语义策略集合计算 Jaccard 相似度。

不要直接用代码文本相似度代替策略相似度。

同时报告哪些具体技术产生重合，哪些技术具有差异。

### Sequential Similarity

根据实际执行的语义操作序列，分析求解顺序差异。

可以使用归一化编辑距离或最长公共子序列。

不同粒度的步骤应说明如何处理。

不要把整个 Blender 程序中的每一行代码当成独立 Agent 操作。

### State Similarity

比较语义相对应的场景状态。

分析物体、部件、空间关系、材质等实际变化。

如果中间检查点不足，不强行计算完整状态轨迹重合度。

### Defect Recurrence

识别同一参考场景中重复出现的缺陷。

例如：

- 相同物体反复遗漏。
- 相同物体反复采用过于简单的建模方式。
- 相同材质反复失真。
- 相同部件反复不衔接。
- 相同空间方向反复错误。

只有具备视觉、代码或几何证据时，才能认为发现了重复缺陷。

区分缺陷相似与原因相似。相同外观问题未必来自相同技术原因。

报告每个场景的实际配对结果，不仅报告汇总平均值。

九个配对来自三个场景，不是九个独立场景样本。不得宣称获得统计显著性或模型普遍行为规律。

## 14. 为后续教师主动探索准备案例

虽然本次不实现教师，但需要从真实实验中筛选值得研究的候选问题。

对于每个候选问题，记录：

- 哪个参考场景。
- 哪个语义物体或部件。
- 哪些学生运行出现问题。
- 实际视觉和几何证据。
- 学生采用了什么建模方法。
- 其他轨迹是否采用不同方法。
- 其他方法是否实际改善问题。
- 可能的技术原因。
- 是否已有足够知识解决。
- 是否值得进一步主动探索。
- 哪些判断仍然无法确认。

例如，如果三个学生都采用相似的家具拼接方法，而且都存在部件不衔接，那么这是一个潜在的主动探索目标。

如果其中一个学生已经自主采用其他方法并取得较好的效果，那么优先记录这个天然对照。

不得在本次实验中加入教师或替学生修改场景来制造成功案例。

- 对三个结果进行排序。
- 描述主要视觉缺陷。
- 指出最应该优先改善的问题。

本次只准备评价材料，不要求用户参与，也不虚构任何人类评分。

## 16. 持续监控

你需要实际运行并持续监控实验，而不是仅生成代码或者启动一个后台命令就结束。

监控：

- Codex CLI 是否正常工作。
- 学生是否真实调用工具。
- Blender 是否正常执行。
- 渲染是否产生。
- CPU、内存和 GPU 占用。
- 模型调用和时间预算。
- 当前任务进度。
- 轨迹文件是否持续保存。

遇到真实工程问题直接定位和修复。

允许修复：

- 路径问题。
- Blender 环境问题。
- CLI 接入问题。
- 图像输入问题。
- 日志记录问题。
- 渲染文件保存问题。
- 任务调度问题。
- 实验评价程序问题。

不允许负责监控的 Codex 替学生完成建模、提供技术 Hint 或修改学生的实际重建结果。

如果出现学生生成错误代码，这是实验现象。应允许学生在既定预算内自行修复，不要由实验控制器代为修复。

如果工程修复改变了正式实验条件，保存旧记录，并注明影响范围。

不要反复重跑直到得到满意图片。

不要影响共享服务器上的其他任务。
