# 如何准备环境并运行

下面的命令都在解压后的 `hint-experiment-handoff/` 根目录执行。最先做 dry-run 看链路，实际复现建议从单题开始。

## 1. 准备运行环境

实际实验建议在 Linux 开发机或原有评测容器中运行，具备 Python 3.12、Bash、可访问的 Docker daemon 和足够内存。生成与解题容器会以 `privileged=True` 启动；如果宿主本身也是容器，需要原框架所要求的 Docker-in-Docker 条件。源码原说明推荐 `is.jd.com/jdea-middleware/cc-run-dind:v1.1`，见 [上游环境说明](../source/benchmark/deepswe/README.md)。

配置模板沿用解题容器 `128g` 的内存限制，verifier 代码使用 `8g`。按机器资源调整 `mem_limit`；较小限制是否够用取决于任务。Mac 可用于阅读和静态检查，完整运行还取决于 Docker 的资源、镜像架构和网络条件。

宿主机依赖安装：

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

这里提供的是依赖安装清单。LiteLLM/SDK/tiktoken 约束参考源码安装模板，历史完整环境没有 lockfile；SDK 等仍有开放版本范围。容器会由 `source/constant_zhy.py` 再安装自己的 Python、Node/SDK、代理依赖和任务项目依赖，宿主机安装成功不等于所有任务容器都已准备好。它需要能访问相应的软件源和模型端点。

## 2. 准备匹配的任务数据

包内没有 DeepSWE 的大型数据、镜像和历史运行日志。优先使用实验团队已有的 Parquet、完整 tasks 目录和任务镜像。

上游说明给出的数据地址是：

- [deep_swe_tasks.parquet](https://joyai-1433141768.cos.ap-beijing.myqcloud.com/huangliang45/deep_swe_tasks.parquet)
- [tasks.zip](https://joyai-1433141768.cos.ap-beijing.myqcloud.com/huangliang45/tasks.zip)
- [DeepSWE 官方仓库](https://github.com/datacurve-ai/deep-swe)

本次打包未验证这些下载地址的当前可用性。若使用它们，可在有网络权限的机器上执行：

```bash
mkdir -p data
curl -fL 'https://joyai-1433141768.cos.ap-beijing.myqcloud.com/huangliang45/deep_swe_tasks.parquet' \
  -o data/deep_swe_tasks.parquet
curl -fL 'https://joyai-1433141768.cos.ap-beijing.myqcloud.com/huangliang45/tasks.zip' \
  -o data/tasks.zip
unzip -q data/tasks.zip -d data
```

解压后检查 `data/tasks/<instance_id>/task.toml`、`tests/Dockerfile`、`tests/test.sh`。如果多了一层目录，就把配置中的 `tasks_dir` 改到**直接包含各任务 ID 目录的那一层**。构建时可能读取更多文件，所以保留完整任务目录。

Parquet 至少应有 `instance_id`、`problem_statement`、`base_commit`、`image_name`。Hint 生成还需 Golden Diff：显式 `golden_diff_file`、任务 `solution/solution.patch` 或 Parquet `patch` 至少有一个有效来源。其余可选列含安装命令与任务隔离命令。配置入口按这些标准列名预检；如果你使用自定义列名，先转换数据，或自行按原 runner 的列名环境变量调整。

任务镜像由 `image_name` 指定；`tests/Dockerfile` 还可能依赖其他基础镜像。请先用自己的账号登录相应镜像仓库，例如：

```bash
docker login is.jd.com
```

若数据使用其他仓库，请登录实际需要的仓库。包内不会自动填写个人 registry 凭据。镜像本身没有被复制到 ZIP。

## 3. 配置模型与路径

```bash
cp config/run.example.json config/run.local.json
```

编辑 `config/run.local.json`：

| 配置 | 要填写什么 |
|---|---|
| `model_name` | 模型端点实际支持的模型名称，替换 `REPLACE_WITH_MODEL_NAME` |
| `api_base` | 可访问的 OpenAI 兼容模型服务根地址或 `/v1` 地址 |
| `api_key_env` | 保存 Key 的环境变量名，默认 `HUBROUTER_API_KEY` |
| `instance_id` | Parquet 中真实存在的任务 ID |
| `run_name` | 输出实验名；基线和 Hint 使用不同名称 |
| `parquet_file`、`tasks_dir` | 本地数据文件和完整任务目录 |
| `output_base` | 输出根目录，默认 `runs` |
| `golden_diff_file` | 单题外部参考补丁，可留空让代码自动查找 |
| `max_rounds` | 外层 Hint 最大尝试次数，默认 5；baseline 每次只跑 1 次 |
| `task_timeout`、`hint_task_timeout` | 一次解题、Hint 生成的超时秒数 |
| `http_proxy`、`no_proxy` | 容器访问软件源需要的代理，默认不配置 HTTP 代理 |

配置里的相对数据/输出路径统一从**包根目录**解析；也支持绝对路径。入口使用当前 Python 解释器，并传给原有子脚本。不要在 JSON 中写 API Key，设置对应环境变量即可：

```bash
export HUBROUTER_API_KEY='<YOUR_API_KEY>'
```

生成、压缩、解题、复盘使用顶层同一个 `model_name`。上游 Shell 和 Python 的默认模型名称不同，历史报告未明确模型；要可比较，必须显式指定并记录实际模型版本。

## 4. 先检查，再跑单题

无需 Key、数据或 Docker，就能查看单题执行链路：

```bash
python3 scripts/run_experiment.py --dry-run --max-rounds 2
```

dry-run 不调用模型，不启动 Docker，不表示题目通过；它会创建步骤日志和摘要。正式运行请换一个 `run_name`，避免把演示日志与真实结果混在一起。dry-run 请使用具体任务 ID，`all` 需要读取外部 Parquet。

准备完环境后先预检：

```bash
python scripts/run_experiment.py --preflight-only
```

预检检查配置、Python 依赖、任务行、验收文件、Golden Diff 来源以及 Docker 连接。它不会预拉镜像或调用模型，因此模型服务、镜像下载和具体测试仍需实际运行验证。

无 Hint 基线（只解题和评测）：

```bash
python scripts/run_experiment.py \
  --mode baseline --instance-id anko-default-function-arguments --run-name baseline_demo
```

Hint 循环（生成→压缩→解题/测试→失败复盘→更新提示→重试）：

```bash
python scripts/run_experiment.py \
  --mode hint --instance-id anko-default-function-arguments --run-name hint_demo
```

退出码：`0`=通过；`1`=正常运行结束但未解出；`2`=配置/步骤异常；`130`=用户中断。不要把 `1` 一概当作程序崩溃，最终结合摘要和 `eval_result.json` 检查。

## 5. 批量处理和续跑

`instance_id=all` 会处理 Parquet 的**全部**题目，不是报告中那 10 道题。报告题目列表在 [results/task_ids.txt](../results/task_ids.txt)。如需跑这 10 道题，可顺序运行，共用一个实验名，源码会按任务 ID 隔离产物：

```bash
while IFS= read -r task_id; do
  if python scripts/run_experiment.py --mode hint --instance-id "$task_id" --run-name hint_10; then
    :
  else
    status=$?
    if [ "$status" -ne 1 ]; then exit "$status"; fi
  fi
done < results/task_ids.txt
```

基线把模式改为 `baseline`，实验名改为 `baseline_10`。比较时记录所有重复基线的运行名称与次数，避免把单次 baseline 和多次 Hint 的差异完全归因于提示。

外层续跑会扫描已完成轮次，复用完整 Hint，补齐缺失复盘，再从下一轮开始：

```bash
python scripts/run_experiment.py --mode hint --run-name hint_demo --continue
```

要只复用生成阶段产物，加 `--skip-hint-gen`，需要相同 `run_name` 下已有 `hint_output.md` 和 `golden_diff.diff`。外层续跑仍会为新轮次开新容器，不是接着修改上一轮代码。

## 6. 到哪里看输出

```text
runs/
  hint_demo/
    hint_gen/<id>/
      golden_diff.diff
      hint_output.md
      hint_compact_r1.md
      hint_compact_r1_meta.json
      hint_compact_r2.md ...
    reviews/<id>/round_1/review_hint_traj.json
    logs/<id>/step_*.log
    loop_summary_<id>.json
  hint_demo_r1/
    infer_logs/<id>/turn_1/
      patch.diff
      trajs.json
      sdk_script.log
      system_prompt_config.json
      system_prompt_actual.json
      eval_result.json
    eval_output/<id>/eval_result.json
  hint_demo_r2/ ...
```

先看 `loop_summary_<id>.json` 的 `solved`、`solved_round`、`final_status`，再打开对应轮的补丁、轨迹、验收结果和 review。保存实际配置、模型版本、数据版本与安装后的 `pip freeze`，才能让后续开发者知道这次运行的条件。运行时原框架会生成包含端点认证信息的临时配置，后续共享运行目录时需要检查这些运行产物。

有真实基线/Hint 运行目录后，可以生成对比 HTML：

```bash
python source/benchmark/deepswe/gen_comparison_report.py \
  --baseline-dir runs/baseline_demo \
  --hint-dir runs/hint_demo \
  --output runs/comparison_report.html
```

`--llm-analyze` 是可选的额外模型调用，默认不启用。包里的 [历史结果](../results/README.md) 是报告转录，不适合作为运行目录传给这个脚本。

## 7. 可选轨迹 DeHint

例如首轮通过时：

```bash
export DEHINT_API_KEY="$HUBROUTER_API_KEY"
export DEHINT_API_BASE='http://hubrouter.jd.com/v1'
export DEHINT_MODEL='<YOUR_MODEL_NAME>'
python source/update_trajs.py \
  --input runs/hint_demo_r1/infer_logs/anko-default-function-arguments/turn_1/trajs.json \
  --actions dehint
```

将 `r1` 改成实际要处理的轮次。输出包含 `dehint/message.json`、`dehint_report.json`、`leak_review.md/json`。保留原轨迹与替换报告；DeHint 只整理记录措辞，不能改变已产生的补丁成绩。

## 常见问题

| 现象 | 优先检查 |
|---|---|
| 预检找不到任务 | `instance_id`、Parquet 版本、tasks 目录层级 |
| Docker 连接失败或拉取 401 | daemon 状态、当前用户 Docker 权限、自己的 registry 登录 |
| 容器初始化失败 | 容器安装日志、软件源/代理、任务依赖、镜像架构 |
| 模型请求 401/404 | Key 环境变量、模型名、端点地址及 `/v1` 路径 |
| Hint 生成找不到答案补丁 | 显式文件、`solution.patch`、Parquet `patch` 三个来源 |
| 有 Hint 文件但疑似未生效 | 实际系统提示日志是否包含 `<system-reminder>` |
| 测试失败而模型说完成 | verifier 日志、reward 和 F2P/P2P，而不是模型自述 |
| 中断后想继续 | 同一实验名使用 `--continue`，核对已保存轮次 |

本包已做静态与 dry-run 检查，没有执行昂贵的模型/Docker 评测；因此不承诺依照当前外部服务就能重现历史的 90%。
