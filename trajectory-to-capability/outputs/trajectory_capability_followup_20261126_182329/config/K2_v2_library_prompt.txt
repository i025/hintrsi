## Updated persistent capabilities

### 1. Preserve state and identity at consumer boundaries
- **Apply when:** a later operation resumes, refines, compares or otherwise consumes earlier state.
- **Constraint:** retain the information, ordering and identity required by that consumer; distinguish already-successful state from new or failed state where the contract requires it. Do not assume a surface identifier survives a lifecycle transition.
- **Method:** inspect representations on both sides; exercise ordinary and continuation paths, incremental repair, and identity changes as relevant. Compare actual consumer inputs or outputs, not invocation count alone.
- **Limits:** not applicable when prior state is deliberately discarded. Evidence: D02 events 30–33, 59–61; D05 events 49–57, 84–85, 95–100, 108–109; Cattrs / `main_agent` / 41–42, 63–64; Snapshot / `main_agent` / 33–45. Snapshot’s lifecycle identity remains incompletely probed.

### 2. Carry and reconcile contracts across representations
- **Apply when:** schemas, typed fields, serialized forms or formatted syntax are consumed in a different representation.
- **Constraint:** preserve meaningful names, ordering, types and behavior according to the actual contract; equivalence checks must operate on meaningful units without disabling unrelated safety checks.
- **Method:** inspect existing adapters and representation helpers; test aliases, missing/extra input and relevant nested or generic cases; rerun earlier reproductions after a targeted repair.
- **Limits:** the correct reconciliation policy is task-specific. Evidence: D06 events 25–26, 27–54, 68–70; D08 events 18–21, 53–63, 78–79; Cattrs / `main_agent` / 43–45, 57–62, 65–84. D06 output was partly truncated; D08’s formal failures remain unexplained.

### 3. Make failures and verification boundaries explicit
- **Apply when:** an operation can partly succeed or has multiple failure modes, prerequisites or consumers.
- **Constraint:** report materially different failures separately from usable output; distinguish an algorithmic failure from a setup problem, empty patch, missing evaluation or stopped work. Never promote a clipped result or focused passing probe to full verification.
- **Method:** inspect outward feedback and downstream inputs; exercise success and relevant failure classes; run focused and regression checks, including earlier reproductions after later edits. Compare with a suitable baseline before attributing a regression, and record which code state each test exercised.
- **Limits:** error semantics and available baselines differ by task. Evidence: D05 events 84–85, 108–109; D02 events 56–62; D06 events 59–63; D08 events 78–79 and formal record; Cattrs / `main_agent` / 71–86; Snapshot / `main_agent` / 29–32, 40–46. The old D05 probes followed actual teacher guidance; no comparable guidance is recorded in the new trajectories.

**Unresolved:** The cause of Snapshot’s one formal change failure and local console failure is not established. Formal success for Cattrs does not prove behavior beyond the evaluated cases. No claim about the relative efficacy of the two arms or a causal effect of this update follows from these independently generated trajectories.
